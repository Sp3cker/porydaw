1. Make Q5's ordering self-evident without cross-section reading: the claim/scope gate and the Empty-is-a-claim semantics currently live in different contract sections (Profile identity vs Publication and observation). 2. Delete QML int-property asymmetry (Q11 vs Q14): HoverHint exposes profile as int while the C++ surface is Id. If HoverHint instead accepted Id through the typed Q_GADGET/Q_ENUM pathway (QML already sees HintProfiles.Empty as an int, so no code change should be needed beyond declaring the property through the metaobject type), the book could drop the 'int' spelling and the 'do not use int fallback' contradiction-adjacent caveat shrinks. Low confidence this is materially simpler; offered because the int spelling is the surface most likely to tempt the forbidden fallback.
3. Reduce Q8's ambiguity by stating the QML non-coupling in the QML section, not only in the ID table: a single sentence 'Native style step-modifier reads affect only the three native spin profiles; no QML or catalogue binding depends on them' would turn Q8's Medium-confidence inference into a stated rule, at zero new-machinery cost.

CONTRADICTIONS / MARKED ITEMS
- Contradiction (mild): 'Each profile describes the complete set of alternatives for a target' (Profile identity) vs. Q8's zero-modifier body case, where the complete NativeSpinBox profile renders EMPTY and only the alternative is removed — the profile is still 'complete' logically but the rendered result is not the full alternatives list. The book handles this via cache-key-on-modifier, which is correct, but the identity sentence is written as if completeness is a rendering invariant; worth an author ruling that 'complete' means 'classified complete', not 'always non-empty rendering'.
- Tension (not a contradiction): the quiz protocol says authors may 'retain a rule only with a concrete reason tied to existing behavior or a simpler overall design' (quiz Purpose), and Q2/Q15's private-ingredient sharing plus no-fragment-builder rule rests on such a concrete reason (one rendering site, semantic IDs, no parallel path). I judge those retained rules justified, not contradicted.
- No unimplementable requirement found: every book answer I traced is realizable from the named files and does not demand a new mechanism the scope paragraph forbids; the closest call was the per-view call_once registration in Q10, which I resolved by reading the existing TimelineQuickView block as per-instance rather than per-process, an [INFERENCE] from task-6 brief wording rather than an explicit book statement.

## Q3 — Blank target
**Book answer:** The no-hint target publishes `Id::Empty` — that is a real, ownership-taking claim with blank text, NOT the same operation as the old target's leave/clear. `publish(source, Empty)` claims the source with blank text; `clear(source)` ends a source's ownership. Moving from a described note to a real no-hint control must not leave the former description up — the Empty claim is what blanks it. Afterward, the new (no-hint) control owns the blank status region until something else claims or its scope clears it. Concrete mechanizers: TimelineInputItem's dispatch fallback publishes Empty (task-4); the popup's direct QString() publication becomes Empty (task 7 step 5); empty rendered text is a cached valid result, not a miss sentinel.
**Evidence:** spec.md “Profile identity” (`Empty = 0` paragraph: “a valid empty description, not the absence of a source; `publish(source, Empty)` claims the source with blank text; `clear(source)` ends that source's ownership. Moving from a described control to a real no-hint control must not leave the former description up”); “Publication and observation” (Empty remains an ownership claim, per task-2 acceptance “Empty remains an ownership claim”); task-1-brief (“valid empty results” cached).
**Natural expectation:** I would have expected a host to simply `clear()` when the pointer leaves a hinted target, treating “no hint” as absence of publication rather than a claim. This is understandable because the popup path (Q5) genuinely needs an owned blank region, and the “moving to a real no-hint control” rule forces the distinction — but it means two identical-looking blank outcomes have different ownership semantics depending on who published, which is the subtlest part of the contract.
**Confidence:** high.

## Catalogue interface and cache

```cpp
class Catalog {

}
```

`MouseHints` owns one `Catalog m_profiles` by value. The catalogue needs no source QObject, application observer, signals, or QML registration of its own instance. ## Evidence and limitations
